## 一个修复任务，为什么会变成会话管理问题

先看一个假设的研发场景。它用于说明设计约束，不是实测案例。

上午，开发者在群聊里说：“导出大文件时程序会卡住，帮忙查一下。”Agent 开始读取代码、复现问题。几分钟后，项目成员在相关 Pull Request（PR，代码合并请求）中提出保留旧接口的要求；持续集成系统（CI）随后报告测试失败；最初的提问者又回到群聊补充：“今天先不要发布，先给出修复方案。”与此同时，Agent 还在处理另一项无关的文档更新。下午，执行测试的机器暂时离线，代码评审却仍在继续。

对人而言，这是同一项修复工作在不同地方出现了新信息，外加一项可以独立推进的工作。对一个只围绕聊天窗口运行的 Agent 而言，却出现了一串组织问题：

- PR 评论与最初的群聊请求，怎样被认作同一项任务？
- 谁有权修改任务约束？“先不要发布”应影响哪个执行者？
- 测试仍在运行时，能否接收新消息并继续修改文档？
- 机器离线后，哪些工作应等待，哪些仍可推进？
- 最后由谁解释总体状态，而不是让几个执行者分别报喜？

即使模型每次都能理解一条消息，这些问题也不会自动消失。它们涉及跨时间的状态、事件归属、执行调度，以及跨信道（群聊、PR、邮件等交互渠道）的协调责任。新的评论还必须经过身份、权限与任务关联检查，不能只因为到达得更晚，就覆盖原任务负责人的决定。

DeepSeek 的《Super-agent 设计探索：迈向更自主的 Agent 系统》讨论的正是这一层问题：当模型承担越来越多具体执行，人仍要在会话之间搬运背景、同步决定、跟踪依赖和催办等待，人的注意力便成为另一项限制。<cite>[1]</cite> 所以这里要优化的不只是模型回答速度，还包括维持整个工作流程所需的人类协调成本。

## 从一次模型推断到一个持续任务

### 模型给出下一步，运行时让下一步发生

在本文讨论的典型工具型系统中，**模型**接收一次输入上下文，生成文本或工具调用请求。输入可以包含指令、对话片段、代码和先前工具结果。模型可以请求“运行测试”，但测试进程的创建、结果收集和错误处理由模型外的软件负责。

**Agent** 则是围绕目标组织模型、工具和反馈的系统。一个常见执行循环如下：

```text
准备上下文 → 调用模型 → 获得动作请求
→ 执行工具 → 收集观察结果 → 更新状态 → 再调用模型
```

ReAct 研究将推理与行动交错组织，使行动获得的环境信息影响后续决策。<cite>[3]</cite> 本文所说的 **Agent Loop** 或 **ReAct Loop**，指这种反复“决策—行动—观察”的执行过程，而不是另一个模型。一项修复可能经过许多轮循环，也可能在中间等待人、测试进程或外部服务。

运行循环的工程软件可称为 **运行时（runtime）**；Agent 工程中的 **Harness** 通常还涵盖模型适配、工具接口、会话记录和执行控制。具体范围因项目而异，本文用它们区分“模型决定采取什么动作”与“软件怎样使动作发生”。DeepSeek Harness 是具体项目；Super-agent 则是在相关基础设施上探索的一种系统组织方式，不能把二者当成同一项已发布功能。

### 会话、上下文与任务各自保存什么

执行循环需要组织历史消息、工具结果和相关执行信息。本文把这样的逻辑交互单元称为 **Session（会话）**。它可以对应聊天界面，也可以隐藏在后台；是否能在进程重启后恢复，取决于系统是否持久化了必要状态。

**上下文（context）** 是本次模型推断实际拿到的工作材料。Session 可以积累很长的历史，但每次调用只能使用有限的上下文窗口。会话里曾经出现过一个决定，不代表这次模型调用一定看到了它。

**任务（task）** 是围绕目标、约束与验收条件组织的工作。“修复导出卡顿，保留旧接口，今天不发布”是一项任务；“检查测试日志”只是其中一个动作。任务可以跨越多个模型调用、工具进程与等待阶段，也可以由多个 Session 协作推进。

| 对象 | 修复案例中的含义 | 不应默认的对应关系 |
| --- | --- | --- |
| 任务 | 修复故障并满足已确认的兼容性与发布约束 | 每条新消息都意味着一项新任务 |
| Session | 某个执行者组织交互历史的逻辑单元 | 聊天窗口、执行会话与任务必须一一对应 |
| 本次上下文 | 当前代码、相关测试结果与有效约束 | 会话全部历史每轮都会自动参与推断 |

用户需要知道任务有没有完成，不一定需要管理后台的 Session；系统却必须知道这些 Session 各自掌握什么、正在等待什么。Super-agent 的设计动机就在这一区别之中。

## 为什么更长上下文或更多 Agent 还不够

### 所有工作放在一个同步会话中

一个简单实现是让单个 Session 接收全部消息，并同步调用工具：只有工具返回后，循环才继续。如果测试运行数分钟，当前循环就在这段时间等待，新指令和无关任务可能一起被阻塞。

增大上下文窗口可以容纳更多历史，却不会自动改变工具等待方式，也不会自动区分两项工作的约束。窗口再长，“暂停发布”仍须关联到正确目标并影响正确动作。同步阻塞是常见实现的选择，不是 ReAct 方法强制要求的定律。

### 每个任务或每条事件各开一个会话

为每项任务保留独立 Session，可以减少上下文混杂。问题随之转移：谁判断后续消息属于哪项任务？谁把 PR 里的兼容性要求同步回群聊发起的修复？如果仍由人完成，系统只是把执行分开，没有接管协调。

进一步为每条新消息创建 Session，容易把 CI 失败、评审意见和暂停请求当成互不关联的新工作。执行者互相不知道已有决定，还可能重复修改同一文件。

这里需要区分 **并发** 与 **并行**：并发是多项尚未结束的任务能够交错推进，不必等一项结束才接受下一项；并行是其中一些计算或工具操作实际同时运行。增加并行资源能提高容量，却不能代替任务归属、共享约束和结果合并。

### 增加一个多 Agent 团队

多 Agent 团队常把复杂工作拆成研究、实现、测试等角色。**Subagent（子代理）** 是被委派去完成一定范围工作的执行者，可以使用自己的上下文和工具。但单个项目内部有分工，并不自然解决项目之外持续到来的消息、跨信道修改需求或长期等待。

如果团队负责人亲自执行大量工作，它仍可能阻塞交互；如果每个成员都直接回复，人又要从局部结论中拼出全局状态。所缺少的，是对“持续协调”和“具体执行”的明确分工，而不只是更多执行者。多代理系统本身也有设计、协作与验证方面的故障，这一点将在后文结合 MAST 研究讨论。<cite>[4]</cite>

## 从持续协作的要求定义 Super-agent

原文提出四个特征。放回前面的案例，它们分别对应明确的系统约束：<cite>[1]</cite>

| 要求 | 对用户意味着什么 | 对系统提出的约束 |
| --- | --- | --- |
| 连续 | 在群聊发起、在 PR 讨论，仍是同一项工作 | 跨信道关联事件与任务，保留有效决定 |
| 高效 | 修复、文档和新指令不必互相等待 | 分离交互与耗时执行，支持受控并发 |
| 主动 | 在已有授权内关注 CI 等变化，必要时继续推进 | 持续接收事件，判断相关性，也能选择不行动 |
| 持久 | 临时重启或环境离线后，任务不被遗忘 | 持久化状态，识别等待条件并安排恢复 |

据此，本文将 **Super-agent** 用作一个有范围的工作定义：**面向持续工作流，能够跨信道维护任务连续性、并发推进工作、按事件适时行动，并在长期运行中保存和恢复必要状态的 Agent 系统。** 它不是统一的学术分类，不表示无限智能，也不直接指代某个模型或正式产品。

以下以 DeepSeek 的设计探索为主要分析对象，先推导机制怎样回应这些约束，再核对公开研究原型的实现边界。设计主张、原型现状和本文工程分析分别说明；架构设想不等同于完整产品承诺。

## Router 与 Worker：让协调者不被执行拖住

既然需要统一交互，又不能让一个会话执行所有工作，就可以拆开两类职责。**Router（路由协调层）** 接住交互、识别任务关系并分派工作；**Worker（执行层）** 在自己的任务上下文中完成具体动作。原文将它们组织成逻辑上的双层架构。<cite>[1]</cite>

| 层次 | 维护的信息和职责 | 在修复案例中做什么 |
| --- | --- | --- |
| Router | 任务之间的关联、关键决定、分派与对外沟通 | 区分修复与文档任务，将经确认的新约束送往相关执行者 |
| Worker | 单项工作的详细上下文、工具反馈与执行进度 | 读取代码、复现卡顿、运行测试并报告结果 |

**路由**决定一条事件应送给谁；**委派**决定由谁承担什么工作、在什么约束下执行。通知某个 Worker 一条消息，并不意味着给它新增发布权限。这个区别会在订阅直通机制中再次出现。

Router 不必理解每一次测试失败的全部细节，但需要知道哪些任务相关、哪些决定影响其他工作，以及什么结果应交给人。文档 Worker 不必收到修复任务的所有编译日志，修复 Worker 也不必携带文档任务的全部历史。这是**上下文隔离**，不自动意味着进程、文件系统或权限隔离。

Worker 内部可以再创建子代理或团队，比如将复现与代码审查分开。这属于单个任务内部的组织；Router/Worker 解决更上层的持续协调，两者可以同时存在。原文选择单个常驻 Router Session，但双层是职责划分，不限制每层只有一个会话。

这一方案也有代价。Router 若误判“暂停发布”属于哪项任务，多个 Worker 可能沿错误方向继续执行。原文观察到较轻量模型能够处理其当前 Router 工作负载，并利用积压事件的批处理缓解压力；这只支持特定负载下的可行性。更大规模可以考虑分片，但全局协调拆开后，又需解决分片之间怎样共享决定。

有了执行者分工，下一个问题是：每次 CI 更新和后续评论，还要让 Router 重新判断并手动转发吗？

## 事件驱动：先识别变化，再把变化送到正确任务

要持续跟进修复，系统必须知道外部发生了什么。接入平台后，收到的通常是一条带来源、时间、对象标识和内容的事件。原文将群聊消息、代码评论、CI 结果等输入称为 **Trigger**：它让系统有机会判断是否需要处理，但不等于一定要行动。<cite>[1]</cite>

同一个 PR、IM 话题或邮件串下的连续事件组成 **Thread**。这里的 Thread 是外部讨论或事件关联单位，不是操作系统线程，也不是模型 Session。修复任务可以同时关联一个群聊 Thread 和一个 PR Thread；同一个 PR Thread 也可能影响多个任务。

因此，**Trigger 描述一次变化，Thread 组织相关事件，任务承载目标，Session 承载执行者的交互状态**。事件驱动意味着变化可以触发后续处理，不必每次都等人进入聊天窗口再发一遍指令。

### 过滤解决“要不要看”，订阅解决“交给谁看”

真实群聊中的大多数消息不需要 Agent 介入。若每条消息都先调用大模型，系统会把大量时间花在决定“不做任何事”上。原文采用两级**事件过滤**：先用程序检查来源、群组范围等确定性规则，再把需要理解语义的候选事件交给模型。

这借用了 **Fast Path / Slow Path（快路径 / 慢路径）** 的思想：已明确的判断由程序低成本完成，不确定的判断才使用模型。快慢描述的是处理路径，不是两种 Agent 智力等级。程序拒绝的事件不必调用模型；通过准入的事件也仍可能在语义判断后被忽略。

另一处快路径发生在**路由**。第一条修复请求尚未明确归属，需要 Router 识别目标并创建 Worker。归属确定后，系统记录 Worker 对相关 Thread 的**订阅**，即“这些事件后续通知这个执行者”的关系。此后同一 PR 的 CI 更新可由程序直接投递给修复 Worker，不必再让 Router 逐次调用工具转发。这就是订阅直通。

以修复任务为例，事件生命周期可以这样理解：

1. 初始群聊请求通过准入与语义判断，Router 将其委派给修复 Worker。
2. Worker 订阅群聊与相关 PR 的 Thread，后续测试、评论直接送达。
3. Worker 根据已确认的约束处理事件；新消息若超出任务范围，可交回 Router 重新分派。
4. Worker 汇报关键进展，Router 统一对外说明；无人需要决策时不必广播全部工具日志。

这是一种按原文机制组织的说明性流程，不承诺平台事件永远有序、只投递一次。工程实现仍需处理重复、乱序与失效订阅。

这里有两个容易在简化架构图中画错的细节：

- **直通不等于 Router 失明。** 原文仍允许 Router 观测全局事件；只是已订阅事件的转发不再依赖它逐次决策。
- **订阅不是一对一绑定。** 一个 Worker 可以订阅多个 Thread，一个 Thread 也可以通知多个 Worker。关键结论仍回到 Router，由它统一面向用户回复。

这种结构与事件驱动系统的发布/订阅思路相通：确定性的归属交给程序，语义不确定性留给模型。共享 Thread 能让 Worker 有机会发现彼此的操作，但**收到相同通知不等于已经具备并发一致性保证**。修改同一分支、同一文档或同一外部对象时，仍可能需要版本校验、冲突检测与合并责任。这一补充属于工程推论，不能视为原文已经解决的能力。

## Inline & Spill：把上下文当成可管理的工作集

事件已经能送到正确执行者，下一步是决定给模型看多少材料。前面区分过 Session 历史与本次上下文：持续工作会累积大量历史，但当前推断只需要其中一部分。把完整 PR、全部日志和每次群聊都注入，会挤占窗口并混入无关信息；只给一个对象 ID，又可能迫使模型反复读取工具。

这里的 **ID** 是能重新定位对象的稳定标识。一个摘要有助于判断“是否值得读”，ID 则提供“到哪里读”的入口；两者承担不同作用。

原文用 **Inline & Spill** 表达这个权衡。**Inline（内联）** 将近期很可能需要的内容直接放进本次上下文，省掉一次读取往返；**Spill（移出工作窗口）** 将长内容或低频细节留在外部，窗口内保留摘要、ID 和续读入口。<cite>[1]</cite> Spill 不等于删除原始数据，也不应留下无法取回完整内容的断头摘要。

它借用了 **Cache（缓存）** 和局部性的思想：处理一条评审意见时，相邻评论、所评审的代码和同一任务的最近决定往往更相关，可以优先内联。但这是信息选择的类比，不代表模型上下文具有硬件缓存的命中、一致性或自动替换保证。

例如，一条代码评审事件可以内联当前评论、相邻评论摘要和 PR 标识，而不是把整个仓库与完整讨论一并塞入。若需要详细背景，再沿入口取回。

当 Trigger、Thread、Worker Session 都有唯一 ID，并在返回对象中附带关联对象的 ID，就形成 **Chain of Recall（链式召回）**：

```text
当前消息 → 所属 Thread → 关联 Worker Session
         → Worker 关联的另一个评审 Thread → 所需历史细节
```

这相当于用对象及其关联构成一张**引用图**：对象是节点，关联 ID 提供通向另一节点的路径。一次读取返回的对象又带有下一跳引用，模型便可逐步找回背景，而不是一次注入全部历史。比如收到 PR 评论后，先找到负责修复的 Worker，再沿其关联找到群聊中“今天不发布”的决定。

这与用关键词或语义相似度直接搜索文档的检索方式不同：这里强调沿已建立的对象关系展开，两类方法可以互补。它也不同于 Chain of Thought（思维链）所讨论的推理过程。关联检索只解决“怎样找回材料”，并未解决永久记忆、正确更新或冲突消解；原文明确将跨月乃至更长周期的记忆列为开放问题。

Anthropic 的上下文工程实践也讨论了按需加载、压缩、结构化笔记和子代理隔离。<cite>[2]</cite> 两者的共同启示是：上下文质量取决于选择与组织，而不只是窗口容量。链式召回的特点则在于对象之间显式可追踪的关联。

进一步落地时，应问几个更细的问题：摘要是否过时？关联对象是否已被删除？引用跨越了哪个权限边界？召回到的决定是否已经被后来版本取代？**能找到历史，不等于找到仍然有效的历史。** 这些需要版本、时效和访问控制配合，不能交给“模型自己记住”来兜底。

## 异步交互：任务等待时，对话不必一起等待

分配多个 Worker 解决了不同任务之间的隔离，但单个 Worker 仍可能卡在耗时工具上。修复 Worker 正在等待测试时，用户发来“先不要发布”；如果必须等测试结束才能处理，关键干预就会被延迟。

这里的**同步调用**是指调用方等待结果后才继续；**异步调用**则先返回一个已启动的状态，让调用方继续处理其他输入，完成结果稍后再送达。二者改变的是等待与调度方式，不改变工具本身需要多长时间运行。

原文将长任务改为由 `start()` 启动、完成事件回传，并提供 `stop()` 停止接口：启动后立即返回 Started；任务在后台运行，最终结果以新事件回到会话；模型可在需要时发出停止请求。新输入在当前推理步结束后即可被处理，无须等待后台工具完成。<cite>[1]</cite>

可以用下面的时序理解这一区别：

```text
同步：发起测试 ── 等待工具结果 ── 处理暂停请求
异步：启动测试 → 处理暂停请求 → 接收测试完成事件
       └──────── 后台测试仍在运行 ────────┘
```

这是机制示意，没有性能测量含义。异步也不等于所有模型推断都在并行：单个会话仍可能顺序处理推理步，多 Worker 是否真正同时执行，还受模型服务和执行环境容量限制。

因此，“全双工”描述的是前台交互与后台执行解耦，**并不意味着正在生成的每一个模型 token 都可被瞬时抢占**。Started 也只表示已经启动，不能当作成功完成。若用户中途改变目标，系统还需要识别旧任务的晚到结果，避免把过时产物继续交付。

`stop()` 也需要谨慎理解。停止请求可能无法瞬间终止远端工作，更不能自动撤销已经产生的外部效果。恢复或重试之前，应结合操作标识和真实状态确认结果；查询暂时没有返回，不足以证明操作从未发生。

### 投机执行：提前准备，不等于提前获准发布

**投机执行（Speculative Execution）** 更进一步：在尚不确定结果是否会被采用时，先在后台复现问题、搜集材料或准备草稿，以额外计算换取更少的人类等待。原文报告了内部群聊中的主动问题处理实践，但这不是对所有公开消息自动行动的通用授权。

这里值得借鉴计算机系统的思想，也需要看到类比的边界：CPU 可以丢弃投机结果，现实系统未必能撤回一封邮件或一次公开发布。本文建议把投机工作优先限制在隔离、可丢弃的草稿和检查中；跨过外部副作用边界之前，再检查授权、目标版本和验收条件。

### 把后台工作转化为人能接住的结果

回到修复案例，用户需要知道的是“问题已复现、兼容性要求已纳入、当前仍未发布”，而非连续几十条读取文件和运行命令的消息。

输出应适配信道。群聊适合简短结果与需要决策的问题；PR、邮件和文档承载完整证据。统一回复出口的意义，不只是少发消息，更是让人不必从多个 Worker 的过程日志中重新拼出一个结论。

## 持久在线，需要拆开计算、状态和执行环境

前面的机制解决了“运行时怎样组织工作”，还没有回答“承载它的进程或机器消失后怎么办”。原文将三件常被捆在本机上的东西分开：<cite>[1]</cite>

- **计算**：此刻推进 Agent Loop 的进程与调度工作，即准备输入、调用模型、处理工具请求。
- **持久状态**：恢复任务所需的已保存信息，如会话记录、任务关系、订阅与执行状态。
- **执行环境**：工具真正作用的机器、文件、仓库、依赖服务与硬件。它也有自己的状态，但不同于会话数据库。

修复任务的“等待测试”记录属于任务状态，测试机上的未提交代码属于执行环境。只备份其中一个，不能声称整个工作都可以无损恢复。

第一步是**计算与状态分离**。Agent Loop 可以运行在可替换的云端计算容器中，Session 等状态保存在数据库。这里“无状态计算”是指必要的持久状态不依赖这个计算实例独占保存，不是说运行中的程序没有临时变量。新的实例可以读取已保存状态继续调度，因此容器重启不必意味着任务历史丢失。

持久化仍需要明确恢复语义。如果外部提交已经成功、数据库却还没有记录成功，重启后直接重放可能造成重复操作。本文的工程建议是保存操作标识、检查点和验收证据，并在恢复时核对外部状态；不确定结果应先确认或交给人处理，而不是假设保存会话就自动获得“恰好执行一次”的保证。

第二步是计算与执行环境分离。真实环境未必容易搬到云端：未提交修改、内网依赖、特定硬件和工具链，都可能使同步不完整。原文提出让环境留在原地，以轻量 **daemon（端侧常驻执行服务）** 接收命令并返回结果；它不负责保存 Agent 的会话历史。云端 Agent 可以连接个人机器，也可以使用托管环境。这使 **BYOM（Bring Your Own Machine，自带执行机器）** 成为一种接入方式，而不必要求用户把完整工作环境迁入云端。

原文还把这一路线与 Anthropic 的 *Scaling Managed Agents: Decoupling the brain from the hands* 联系起来。后者同样分离 Harness、会话日志和执行接口，但主要面向托管环境；这里特别关心带有本地状态、可能间歇在线的个人设备。共同的分离原则，不意味着两者部署假设或实现已经相同。<cite>[7]</cite>

这个设计让“Agent 持续在线”与“某台执行设备暂时离线”成为不同状态。它并不让离线机器上的任务凭空继续执行；需要该环境的工作仍须等待环境恢复，或明确切换到另一个满足条件的环境。

### Watchdog：区分进程存活与任务进展

即使状态可以恢复，系统也可能长时间“正常运行但没有进展”：修复 Worker 反复运行同一失败命令，文档 Worker 不断重写同一个段落。普通的存活探测只能知道进程是否响应，无法充分判断任务有没有推进。

**Watchdog（看门狗）** 在这里指独立于主执行流程的监督者。原文将其实现为独立 Session，用定时事件驱动一个外部**控制回路**：观察系统状态，与预期目标比较，必要时介入，再继续观察。它既关注接口错误、恢复失败，也尝试判断 Worker 有没有实质进展、是否偏离任务目标。<cite>[1]</cite>

这一思路抓住了 Agent 的特殊故障：进程和 API 都正常，任务却可能不断重复无效动作。但模型判断进展同样会出错，Watchdog 也不是万能的监督者。本文建议把“最近新增了什么可验证产物”“同一失败是否重复”“是否超过预算”等可观察信号与语义判断结合，并约束自动修复的权限。否则监督层可能变成另一个有完整工具、但缺少制约的行动者。

跨设备连接也扩大了风险范围。环境事件可能携带提示词注入，端侧又可能保存私有代码与凭据。原文已明确承认安全和隐私问题尚未解决。系统应将事件内容视为数据，而不是新的授权来源；凭据尽量通过受控机制使用，不直接进入模型上下文；日志还应限制敏感内容、访问范围与保留期限。

## 初步实验支持什么，又没有支持什么

架构解释成立，不等于收益已经被充分测量。原文第一组实验采用**消融比较**：在相近任务负载下移除某项机制，观察结果怎样变化，以帮助识别机制贡献。它比较完整方案、去掉订阅直通的方案，以及两种提示词下的单 Session 加 Subagent 工具方案。

端到端消融使用约 300 条群聊与 GitHub CI 消息，其中约 20 条是工作请求；**编码工作被只消耗时间的工具替代**，每种方案重复 5 次。消息间隔与工作时长按四分之一缩放，模型调用耗时保持真实值。完成时间指从工作请求到结果消息的耗时；仅有 5 次重复，且原文未报告统计检验，本文不据此断言统计显著性或生产稳定性。<cite>[1]</cite>

其中 p50 表示报告分布的中位完成耗时，p95 描述较慢尾部的第 95 百分位；它们不是成功率。读缓存 token 是原文统计的缓存读取量，不等于全部 token 或实际费用。

| 原文报告 | 可以说明什么 | 不能推出什么 |
| --- | --- | --- |
| Super-agent 完成耗时 p50 为 12.4 分钟、p95 为 15.7 分钟 | 在该合成负载与配置下的调度表现 | 真实编码任务的质量、通用速度或生产 SLA |
| 中性提示的单 Session 基线，5 次均未调用 Subagent | 在该设置中，临场委派受提示和模型行为影响 | 所有单 Session 系统都不会正确委派 |
| 去掉直通后，耗时基本一致，Router 决定数约增 30%，读缓存 token 从 2323 万增至 3177 万 | 直通在该负载下节省路由决策与读缓存 token 开销 | 直通已经提高了任务质量或完成速度 |

这组实验中，系统约束 Router 不亲自执行，比只用提示词劝主会话委派更稳定；同时，多会话方案付出了更多读缓存 token。合理的结论是一个**调度时延与读缓存 token 开销之间的权衡**，不是“多 Agent 全面胜出”。

第二组压力测试使用真实 Router 模型与 **Mock Worker（模拟执行者）**，将执行端简化，集中观察路由端负载；观察到事件增多时积压事件自动形成批处理，单个决定分摊的推理开销下降。它支持作者在当时团队规模下暂不急于切分 Router 的选择，但不能证明无限吞吐。引用这些实验数字时，也应明确它们是原文作者报告，本文未独立复现。

MAST 对多代理故障的研究，将问题归纳为系统设计、代理间失配和任务验证三类；它提醒我们调度更快之外仍有协作失败。<cite>[4]</cite> τ-bench 则关注最终数据库状态及重复试验的一致成功，而不仅是助手是否回复“已完成”。<cite>[5]</cite>

由此可以提出后续评测：保留合成事件负载，同时加入有真实验收条件的任务，固定模型、预算与工具权限，记录成果正确性、重复可靠性、尾延迟、token、人工介入和权限违规；再注入重复事件、乱序、设备断线与用户叫停。这里是本文的评测建议，不是原文已经完成的实验。

## 开源原型与完整愿景之间仍有距离

公开的 `deepseek-ai/dsh-superagent-prototype` 仓库采用 MIT 协议，但 README 明确说明：它是研究原型，不是 DeepSeek 的正式产品，也不是生产就绪的软件。公开代码经过适配，与内部系统及文章描述不完全一致，文章中的部分设计尚未实现。<cite>[6]</cite>

其可用范围聚焦于单个 GitHub 仓库的主动编码协作，可选接入飞书，并提供 Worker 会话/目录与需要人介入的 Web 面板。原型把工作组织为 Ticket（任务条目），使用 profile 区分运行配置；这些是具体实现术语，不是 Super-agent 定义本身。下面固定到提交 `6337fc8` 核对设计与实现，避免把可变仓库首页当成永久能力说明：

| 关注点 | 原文设计 | 公开原型文档显示的边界 |
| --- | --- | --- |
| Router 工具 | 可不配 Bash，专注轻量协调 | 主会话实际拥有 Bash、read 和 job 工具；避免亲自读代码主要依赖提示规则，而非撤销工具权限 <cite>[8]</cite> |
| 事件直通 | 已订阅 Thread 的事件直接进入 Worker | 文档明确：直通提供上下文，不授予行动权限；事件准入不等于操作授权 <cite>[9]</cite> |
| 持久状态 | 计算、状态与执行环境分离 | 文档给出 SQLite 状态存储、目录锁与每 Ticket 的会话/目录；不能据此宣称完整云端 BYOM 架构已实现 <cite>[8]</cite> |
| 外部恢复 | Watchdog 判断故障和任务进展 | 部署文档提供由操作者设置的独立 profile 定时恢复检查；不应把它写成完整语义监督已自动启用 <cite>[10]</cite> |

尤其需要注意，部署文档说明两类预设使用 `danger-full-access`，以操作者的操作系统身份运行。凭据包装脚本提供默认选择，不构成文件或进程隔离；Worker 仍可能访问该身份可访问的主目录和路径。文档建议使用专用操作系统账户。<cite>[10]</cite> 因而本文不把默认启动方式作为安全部署建议，也不提供一键接入真实凭据的命令。

阅读这个原型，更适合追踪“哪些对象、事件和调度机制已落到代码”，而不是依据架构图假设完整的跨设备个人助手已经开箱可用。

## 回到最初的修复任务

现在可以重新走一遍开篇场景。群聊请求成为 Trigger，经检查后关联到一个任务；Router 委派修复 Worker，同时让文档工作独立推进。相关 PR 和群聊 Thread 的事件通过订阅送达，必要时沿引用图找回之前的决定。后台测试以异步方式运行，暂停发布的授权指令可以在工具结束前被处理；晚到的测试结果仍需按当前任务状态解释。

测试机离线时，系统保存等待条件，而不是宣布修复完成。机器恢复后，需要确认代码版本和外部操作状态，再决定继续执行。Watchdog 可以发现长期无进展，但是否采取修复动作仍受权限和证据约束。最终由 Router 给出统一结果，将详细证据放到合适的工作界面，让人作必要决策与验收。

这条流程将全文机制连到同一个目标：**把任务连续性从人的记忆搬到可管理、可核查的系统状态中。** 模型能力决定它能理解和解决哪些问题；运行时决定怎样行动；更上层的协调架构决定多个问题怎样在时间、信道和环境变化中持续推进。更强的模型与更好的系统设计相互补充，不能互相替代。

若要继续深入具体执行设施和委派隔离，可参见 [Harness Engineering]({% post_url 2026-05-22-harness-engineering-agent-kernel %}) 与 [Subagent 架构]({% post_url 2026-05-22-subagent-architecture-isolation %})。评价 Super-agent 时，则需要同时追问：任务身份是否清楚、最新约束是否有效、结果是否可验证，以及异常时究竟该继续、等待、停止，还是交还给人。
